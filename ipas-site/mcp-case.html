MCP 案例：把訂單系統包成 MCP Server

模型上下文協定（Model Context Protocol, MCP）是 AI 應用連接工具與資料的開放標準。本頁用「電商退款 Agent」當案例，從架構、可執行的 Python 程式、線路上實際傳送的 JSON-RPC 訊息，到安全設計與考點，一次看懂 MCP。所有輸出都是實際執行程式得到的結果。

為什麼要 MCP架構案例情境Server 程式Client 程式JSON-RPC 訊息接上 AI 應用安全設計易混淆比較考點自我檢測
01 為什麼要 MCP

從 N×M 條膠水程式，變成 N+M 個標準介面

公司有客服助理、報表機器人、程式碼助理 3 個 AI 應用，都要用訂單、物流、金流 3 個系統。沒有標準時，每個應用都要各寫一次串接：3 × 3 = 9 段客製程式，系統一改就要改 3 個地方。有了 MCP，每個系統只要包成一個 MCP Server，每個應用只要內建一個 MCP Client：3 + 3 = 6 個元件，而且新系統接上後所有應用都能用。

2024-11Anthropic 發布並開源 MCP 規格
JSON-RPC 2.0訊息格式：請求、回應、通知
3 種能力Tools、Resources、Prompts
2 種傳輸stdio（本機）、Streamable HTTP（遠端）

常見比喻：MCP 是「AI 應用的 USB-C」或「貨櫃標準」。各家只要遵守同一個介面形狀，不必知道對方內部怎麼做。MCP 不取代 API，Server 底下仍然是呼叫原本的 API 或資料庫；MCP 是讓 AI 應用用同一種方式「找到並使用」這些 API 的那一層。

02 架構

Host、Client、Server 三個角色

能力由誰控制用途本案例
Tools 工具模型（Model-controlled）執行動作、可能有副作用lookup_order、check_shipping、issue_refund
Resources 資源應用程式（Application-controlled）提供可讀取的資料，以 URI 識別policy://refund、orders://{order_id}
Prompts 提示範本使用者（User-controlled）預先寫好的任務範本，例如選單或斜線指令damaged_item_reply
傳輸方式運作適合
stdioHost 把 Server 當子程序啟動，用標準輸入／輸出一行一則 JSON 訊息本機工具、開發測試；不需網路與埠號
Streamable HTTPServer 是獨立的網路服務，用 HTTP POST 傳訊息，可串流回應遠端、多使用者共用；需搭配 OAuth 授權（舊版的 HTTP+SSE 已由它取代）

連線生命週期

  1. initialize：Client 送出支援的協定版本與能力，Server 回覆自己的版本、能力與 instructions
  2. notifications/initialized：Client 通知握手完成（通知沒有 id，不需回應）
  3. 探索：tools/list、resources/list、prompts/list
  4. 使用：tools/call、resources/read、prompts/get
  5. 結束：關閉傳輸（stdio 就是結束子程序）
03 案例情境

Cloud X Berry 的退款 Agent

顧客寫信：「訂單 4471 的果汁機送到時裂了，可以退款嗎？」客服 Agent 需要查訂單、查物流、看退款政策，符合規定才退款；超過 3,000 元要主管核准。訂單團隊決定把訂單系統包成一個 MCP Server，讓客服助理、報表機器人、工程師的程式碼助理都能共用。

設計需求對應的 MCP 設計
Agent 要能查訂單與物流唯讀工具，標註 readOnlyHint
Agent 要能退款，但不能亂退寫入工具，標註 destructiveHint；金額上限寫在程式碼
付款服務逾時後重試不可重複退款工具參數加入冪等鍵 idempotency_key
退款政策會改版，要能引用做成 Resource，由應用程式讀取後放入上下文
客服人員要一鍵套用處理流程做成 Prompt 範本
每筆退款要留稽核紀錄Server 端寫日誌到 stderr
⬇ 下載完整程式 mcp-case.zip

壓縮檔內含 order_server.py、demo_client.py、raw_jsonrpc.py。安裝：pip install "mcp>=2"，解壓後在同一個資料夾執行 python demo_client.py。本頁以 MCP Python SDK 2.3.0 實測；1.x 版的 FastMCP 在 2.x 改名為 MCPServer，其餘寫法幾乎相同。

04 Server 程式

order_server.py 逐段解說

SDK 會讀取函式的名稱、型別提示與 docstring，自動產生工具的 name、description 與 inputSchema（JSON Schema）。所以寫清楚 docstring 就是在寫「給模型看的工具說明」。

步驟 1　建立 Server 與後端資料

Python
import logging
import sys
import uuid
from datetime import date

from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

# ------------------------------------------------------------
# 1. 建立 Server：名稱與 instructions 會在初始化時告訴 Client
# ------------------------------------------------------------
mcp = MCPServer(
    name="order-system",
    instructions="Cloud X Berry 商店的訂單系統。查詢訂單後再決定是否退款；"
                 "退款金額超過 3,000 元必須由主管核准。",
)

# stdio 模式下 stdout 專門傳 JSON-RPC 訊息，任何 print 都會弄壞協定；
# 日誌一律寫到 stderr（Host 會收集成 Server 日誌）
logging.basicConfig(stream=sys.stderr, level=logging.INFO, format="%(asctime)s %(message)s")
log = logging.getLogger("order-system")

# 模擬後端資料庫（實務上這裡會呼叫公司原本的 REST API 或資料庫）
ORDERS = {
    "4471": {"customer": "C001", "item": "果汁機", "amount": 2490, "sale_item": True,
             "delivered": "2026-11-05", "status": "delivered"},
    "4480": {"customer": "C002", "item": "空氣清淨機", "amount": 8900, "sale_item": False,
             "delivered": "2026-11-02", "status": "delivered"},
    "4492": {"customer": "C001", "item": "電動牙刷", "amount": 1290, "sale_item": False,
             "delivered": None, "status": "shipping"},
}
REFUND_LIMIT = 3000          # 自動退款上限（業務規則寫在程式碼，不靠提示詞）
ISSUED: dict[str, str] = {}  # 冪等鍵 → 退款單號，避免重試造成重複退款

instructions

初始化時傳給 Client，Host 可放進系統提示，告訴模型這個 Server 的用途與規則。

stdout 不能亂印

stdio 模式下 stdout 專門傳 JSON-RPC。程式裡任何 print() 都會插進協定訊息讓 Client 解析失敗，這是新手最常見的錯誤。日誌一律寫到 stderr。

上限寫在程式碼

REFUND_LIMIT 是業務規則。寫在提示詞只是「請求」模型遵守，寫在 Server 程式才是「強制」。

步驟 2　唯讀工具

Python
# ------------------------------------------------------------
# 2. Tools：模型決定何時呼叫。函式簽名與 docstring 會自動轉成
#    name / description / inputSchema（JSON Schema）
# ------------------------------------------------------------
@mcp.tool(annotations=ToolAnnotations(read_only_hint=True))
def lookup_order(order_id: str) -> dict:
    """依訂單編號查詢訂單內容、金額、是否為特價品與配送狀態。"""
    order = ORDERS.get(order_id)
    if order is None:
        raise ToolError(f"找不到訂單 {order_id}")   # 錯誤以簡短訊息回傳給模型
    return {"order_id": order_id, **order}


@mcp.tool(annotations=ToolAnnotations(read_only_hint=True))
def check_shipping(order_id: str) -> str:
    """查詢訂單目前的物流狀態。"""
    order = ORDERS.get(order_id)
    if order is None:
        raise ToolError(f"找不到訂單 {order_id}")
    if order["status"] == "delivered":
        return f"已於 {order['delivered']} 送達"
    return "配送中，預計 2 個工作天內送達"

查無資料時丟出 ToolError，SDK 會把它轉成 isError: true 的工具結果，讓模型讀到簡短錯誤後自行調整，而不是讓整個連線出錯。readOnlyHint 告訴 Host 這個工具不會改變資料，Host 可以據此決定不必每次都詢問使用者。

步驟 3　有副作用的退款工具

Python
@mcp.tool(annotations=ToolAnnotations(destructive_hint=True, idempotent_hint=True))
def issue_refund(order_id: str, amount: int, reason: str, idempotency_key: str) -> dict:
    """對已送達的訂單申請退款。amount 不可超過訂單金額；
    idempotency_key 為每次退款請求的唯一值，重試時請沿用同一個值。"""
    # (a) 冪等：同一個 key 重送，直接回傳上次結果，不會退兩次
    if idempotency_key in ISSUED:
        return {"status": "already_processed", "refund_id": ISSUED[idempotency_key]}

    # (b) 驗證輸入值是否合理
    order = ORDERS.get(order_id)
    if order is None:
        raise ToolError(f"找不到訂單 {order_id}")
    if order["status"] != "delivered":
        raise ToolError("訂單尚未送達，不能退款")
    if not 0 < amount <= order["amount"]:
        raise ToolError(f"退款金額必須介於 1 到 {order['amount']} 元")

    # (c) 業務規則：超過上限不執行，改為送審（human-in-the-loop）
    if amount > REFUND_LIMIT:
        log.info("訂單 %s 退款 %s 元超過上限，已轉主管核准", order_id, amount)
        return {"status": "pending_approval",
                "message": f"金額超過 {REFUND_LIMIT} 元，已送主管核准，核准後才會退款"}

    # (d) 真正執行（實務上是呼叫金流系統 API）
    refund_id = "RF-" + uuid.uuid4().hex[:8].upper()
    ISSUED[idempotency_key] = refund_id
    order["status"] = "refunded"
    log.info("已退款 %s 元，單號 %s，原因：%s", amount, refund_id, reason)   # 稽核紀錄
    return {"status": "refunded", "refund_id": refund_id, "amount": amount}
程式區塊防範的問題
(a) 冪等鍵付款逾時後 Agent 重試，造成同一筆退兩次
(b) 輸入驗證模型傳入不存在的訂單、未送達的訂單、超過訂單金額的數字
(c) 金額上限模型被說服或被提示注入後要求大額退款；超過上限一律轉人工
(d) 稽核日誌事後追查誰在何時退了多少、原因是什麼

工具註記（Annotations）如 destructiveHint、idempotentHint 只是提示，讓 Host 決定要不要先請使用者確認。規格明確說明 Client 不應完全信任來自不受信任 Server 的註記；真正的防線是 Server 程式裡的檢查。

步驟 4　Resources 與 Prompts

Python
# ------------------------------------------------------------
# 3. Resources：由 App 決定何時讀取，用 URI 識別，適合放文件與資料
# ------------------------------------------------------------
@mcp.resource("policy://refund", mime_type="text/markdown")
def refund_policy() -> str:
    """退款政策（第 4 版）"""
    return ("# 退款政策 v4（2026-10-25 生效）\n"
            "- 到貨 30 天內可申請退款。\n"
            "- 特價品原則上不退，但到貨時已損壞者可全額退款。\n"
            f"- 單筆退款超過 {REFUND_LIMIT} 元需主管核准。\n")


@mcp.resource("orders://{order_id}")
def order_resource(order_id: str) -> dict:
    """單筆訂單資料（資源範本：URI 中的 {order_id} 是參數）"""
    return ORDERS.get(order_id, {})


# ------------------------------------------------------------
# 4. Prompts：由使用者挑選的範本，回傳要送給模型的訊息
# ------------------------------------------------------------
@mcp.prompt()
def damaged_item_reply(order_id: str, customer_name: str) -> str:
    """處理「商品到貨損壞」客訴的標準流程範本"""
    return (f"顧客 {customer_name} 反映訂單 {order_id} 到貨損壞。請依序：\n"
            "1. 呼叫 lookup_order 確認訂單與到貨日；\n"
            "2. 讀取 policy://refund 確認規定；\n"
            "3. 符合規定才呼叫 issue_refund，並用禮貌、簡短的語氣回覆顧客。\n"
            f"今天日期：{date.today().isoformat()}")

policy://refund 是固定資源；orders://{order_id} 含參數，會註冊成「資源範本」。政策做成資源的好處：應用程式可在對話開始時就讀進上下文並顯示版本號，模型回答時能引用；政策改版只要更新 Server。

05 Client 程式

demo_client.py：模擬 Host 走完一次流程

真正的 Host 會把工具清單交給 LLM，由 LLM 決定呼叫哪個工具。這支程式把「LLM 的決定」寫死，方便逐步觀察請求與回應。

Python
"""
demo_client.py — 模擬 Host 內的 MCP Client，連線到 order_server.py

實際產品中，Host（例如 Claude Desktop、IDE 的 AI 助理）會：
  1. 啟動 Server 並完成初始化握手
  2. 把 tools/list 拿到的工具描述交給 LLM
  3. LLM 決定要呼叫哪個工具 → Client 送出 tools/call → 結果再交回 LLM
這支程式把「LLM 的決定」寫死，方便觀察每一步的請求與回應。
執行：python demo_client.py
"""
import asyncio
import json
import sys

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

# Host 用子程序啟動 Server；Server 的 stderr 日誌會直接顯示在終端機
SERVER = StdioServerParameters(command=sys.executable, args=["order_server.py"])


def show(title, obj):
    print(f"\n=== {title} ===")
    print(obj if isinstance(obj, str) else json.dumps(obj, ensure_ascii=False, indent=2))


def text_of(result):
    """取出工具回傳的文字內容；isError=True 代表工具執行失敗"""
    body = "\n".join(c.text for c in result.content if getattr(c, "text", None))
    return ("[錯誤] " if result.is_error else "") + body


async def main():
    async with stdio_client(SERVER) as (read, write):
        async with ClientSession(read, write) as session:
            # 1) 初始化：交換協定版本與雙方能力
            init = await session.initialize()
            show("1. initialize", {"server": init.server_info.name,
                                   "protocol": init.protocol_version,
                                   "instructions": init.instructions})

            # 2) 探索：列出工具、資源、資源範本、提示範本
            tools = await session.list_tools()
            show("2a. tools/list", [{"name": t.name,
                                     "description": t.description,
                                     "required": t.input_schema.get("required"),
                                     "annotations": t.annotations.model_dump(exclude_none=True)
                                     if t.annotations else None} for t in tools.tools])
            res = await session.list_resources()
            tpl = await session.list_resource_templates()
            prm = await session.list_prompts()
            show("2b. resources / templates / prompts", {
                "resources": [str(r.uri) for r in res.resources],
                "templates": [t.uri_template for t in tpl.resource_templates],
                "prompts": [p.name for p in prm.prompts]})

            # 3) 讀取資源：App 把政策文件放進上下文
            policy = await session.read_resource("policy://refund")
            show("3. resources/read policy://refund", policy.contents[0].text)

            # 4) 取得提示範本：使用者在介面上選了「到貨損壞」範本
            p = await session.get_prompt("damaged_item_reply",
                                         {"order_id": "4471", "customer_name": "王小姐"})
            show("4. prompts/get damaged_item_reply", p.messages[0].content.text)

            # 5) 模型決定呼叫工具：先查訂單、再查物流
            r = await session.call_tool("lookup_order", {"order_id": "4471"})
            show("5a. tools/call lookup_order", text_of(r))
            r = await session.call_tool("check_shipping", {"order_id": "4471"})
            show("5b. tools/call check_shipping", text_of(r))

            # 6) 退款：同一個冪等鍵送兩次，模擬逾時後重試
            args = {"order_id": "4471", "amount": 2490, "reason": "到貨損壞",
                    "idempotency_key": "req-4471-001"}
            r = await session.call_tool("issue_refund", args)
            show("6a. tools/call issue_refund", text_of(r))
            r = await session.call_tool("issue_refund", args)
            show("6b. 重試（同一個 idempotency_key）", text_of(r))

            # 7) 超過上限：不執行，轉人工核准
            r = await session.call_tool("issue_refund", {
                "order_id": "4480", "amount": 8900, "reason": "不喜歡",
                "idempotency_key": "req-4480-001"})
            show("7. 超過 3,000 元上限", text_of(r))

            # 8) 錯誤處理：訂單不存在、金額不合理
            r = await session.call_tool("lookup_order", {"order_id": "9999"})
            show("8a. 訂單不存在", text_of(r))
            r = await session.call_tool("issue_refund", {
                "order_id": "4492", "amount": 1290, "reason": "等太久",
                "idempotency_key": "req-4492-001"})
            show("8b. 尚未送達", text_of(r))


if __name__ == "__main__":
    asyncio.run(main())

06 JSON-RPC 訊息

拿掉 SDK，看線路上實際傳了什麼

stdio 傳輸就是一行一則 JSON 訊息。下面這支程式不使用 SDK，直接寫 JSON-RPC 2.0 訊息給 Server。

Python
"""
raw_jsonrpc.py — 不用 SDK，直接用 JSON-RPC 2.0 和 MCP Server 對話
用來看清楚線路上實際傳了什麼：stdio 傳輸是一行一個 JSON 訊息。
執行：python raw_jsonrpc.py
"""
import json
import subprocess
import sys

proc = subprocess.Popen([sys.executable, "order_server.py"], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True,
                        encoding="utf-8")


def send(msg):
    print(">>>", json.dumps(msg, ensure_ascii=False))
    proc.stdin.write(json.dumps(msg) + "\n")
    proc.stdin.flush()


def recv():
    line = proc.stdout.readline()
    msg = json.loads(line)
    print("<<<", json.dumps(msg, ensure_ascii=False)[:600])
    return msg


# 1. 初始化請求（有 id → 需要回應）
send({"jsonrpc": "2.0", "id": 1, "method": "initialize",
      "params": {"protocolVersion": "2025-11-25", "capabilities": {},
                 "clientInfo": {"name": "raw-client", "version": "0.1"}}})
recv()
# 2. 初始化完成通知（沒有 id → 通知，不需回應）
send({"jsonrpc": "2.0", "method": "notifications/initialized"})
# 3. 列出工具
send({"jsonrpc": "2.0", "id": 2, "method": "tools/list"})
recv()
# 4. 呼叫工具
send({"jsonrpc": "2.0", "id": 3, "method": "tools/call",
      "params": {"name": "check_shipping", "arguments": {"order_id": "4471"}}})
recv()
# 5. 呼叫不存在的訂單 → isError: true（工具錯誤，不是協定錯誤）
send({"jsonrpc": "2.0", "id": 4, "method": "tools/call",
      "params": {"name": "lookup_order", "arguments": {"order_id": "9999"}}})
recv()
# 6. 呼叫不存在的方法 → JSON-RPC error（協定錯誤）
send({"jsonrpc": "2.0", "id": 5, "method": "orders/delete", "params": {}})
recv()
proc.terminate()

訊息類型特徵例子
請求 Request有 id 與 method，必須回應initialize、tools/call

08 安全設計

連得上不等於可以做

風險情境對策本案例做法
超額授權Server 用管理員帳號連資料庫，可以刪單最小權限：Server 只拿完成任務所需的權限只提供查詢與退款，沒有刪除工具
工具描述投毒（Tool Poisoning）第三方 Server 的工具描述藏有「順便讀取使用者金鑰」等隱藏指令只安裝信任來源的 Server、審查描述、鎖定版本Server 由公司自行開發與維護
間接提示注入顧客留言或文件內容要求 Agent「全額退款到另一個帳戶」規則寫在程式碼、敏感操作需人工核准金額上限與送審邏輯在 Server 內
重複執行逾時重試造成重複扣款或退款冪等鍵idempotency_key
遠端存取未授權Streamable HTTP Server 暴露在網路上OAuth 2.1 授權、HTTPS、驗證來源本機 stdio，正式上線改 HTTP 時需加上
無法追查退款出錯不知道是哪一步記錄每次工具呼叫的參數、結果與使用者stderr 稽核日誌
工具過多連太多 Server，工具描述塞滿上下文，模型選錯工具只連需要的 Server、工具名稱與描述清楚、可配合 Skills 漸進載入只有 3 個用途分明的工具
09 易混淆比較

MCP 和其他名詞的差別

名詞解決的問題和 MCP 的關係
Function Calling／Tool UseLLM 如何輸出結構化的工具呼叫請求模型端的能力；MCP 負責把工具「提供」給應用，兩者搭配使用
REST API系統之間交換資料MCP Server 底下通常就是呼叫 API；MCP 不取代 API
Agent Skills這類任務「該怎麼做」的流程知識，需要時才載入Skill 是做法，MCP 工具是手段；Skill 執行時常會用到 MCP 工具
A2A（Agent2Agent）不同 Agent 之間互相委派任務與溝通MCP 是 Agent 連工具與資料（垂直），A2A 是 Agent 連 Agent（水平）
RAG從文件中檢索相關內容補充上下文檢索系統可以包成 MCP 工具或資源提供給 Agent
AI Gateway管控所有模型呼叫的身分、預算、路由與紀錄管的是「Host 呼叫模型」；MCP 管的是「Host 呼叫工具」，兩者都需要
10 考點

中級可能的考法

  1. 角色辨識：使用者操作的 AI 應用是 Host；Host 內負責連線的是 Client；包住後端系統的是 Server。
  2. 三種能力的控制者：Tools 由模型、Resources 由應用程式、Prompts 由使用者決定。
  3. 傳輸選擇：本機子程序用 stdio；遠端多人共用用 Streamable HTTP 並加 OAuth。
  4. 效益計算：N 個應用 × M 個系統，客製整合 N×M、MCP 只需 N+M。
  5. 安全情境：連上 MCP 不代表有權限，業務規則與上限要在 Server 或控制迴圈中強制。
  6. 錯誤判讀：工具錯誤（isError）與協定錯誤（JSON-RPC error）的差別。
  7. 名詞比較：MCP vs Function Calling vs A2A vs Skills。
