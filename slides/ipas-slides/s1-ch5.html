5.1 資料準備 ｜ 資料清理

先補洞，再抓怪值

科目一 · 第五章 AI 技術應用與系統部署 ｜ 03 ｜ 示意資料；統計量由程式計算

資料清理先處理遺漏值。左邊體重欄位有兩格缺值：均值填補用其餘六筆的平均值約七十一點三公斤補上；前向填補則用前一筆的值，適合時間序列；也可以用中位數或線性插補。右邊是異常值：十天的訂單數中有一天是一百二十。IQR 法算出第一四分位數約五十二點三、第三四分位數約五十七點八，上界約六十六，一百二十超過上界；Z 分數約二點九六，接近三，兩種方法都把它標為異常。進階方法還有 Isolation Forest 和 LOF，重複值則用 drop_duplicates 移除。

5.1 資料準備 ｜ 特徵工程

把原始欄位變成模型讀得懂的數字

科目一 · 第五章 AI 技術應用與系統部署 ｜ 04 ｜ 示意資料；轉換由程式計算

特徵工程把原始欄位轉成模型讀得懂的數字。左邊是編碼：城市這種沒有順序的類別用 One-hot，每個城市一個欄位，是就填一、不是填零；如果用 Label Encoding 編成零、一、二，模型會誤以為高雄比台北大。右邊是標準化：Min-Max 把數值壓到零到一，但會被極值一百八十影響，前四筆都擠在零點三以下；Z-score 讓平均為零、標準差為一。特徵選擇可以用 Information Gain、Pearson 相關係數或 L1 正則化的 Lasso。

5.1 資料準備 ｜ PCA 降維

找出變異最大的方向，用更少維度保留資訊

PCA

線性降維：找變異最大且彼此正交的主成分

t-SNE／UMAP

非線性，保留局部鄰近關係 → 用於視覺化

考點：t-SNE／UMAP 不適合當後續建模的輸入；PCA 可以

AutoML

自動做特徵工程、模型選擇、超參數調優：Google AutoML、H2O.ai、AutoKeras、TPOT

科目一 · 第五章 AI 技術應用與系統部署 ｜ 05 ｜ 模擬資料；主成分由共變異數矩陣計算

PCA 主成分分析找出資料變異最大的方向當作第一主成分，第二主成分和它正交。左圖一百二十個模擬點沿著斜線分布，程式從共變異數矩陣算出主成分方向，第一主成分就保留了約九成的變異，所以把點投影到 PC1 上，從二維降到一維也損失很少。t-SNE 和 UMAP 是非線性降維，保留局部鄰近關係，適合視覺化，但不適合當後續建模的輸入。AutoML 則把特徵工程、模型選擇和超參數調優自動化，代表工具有 Google AutoML、H2O.ai、AutoKeras、TPOT。

5.1 模型選擇 ｜ 主要任務類型

先看輸出是什麼，再選演算法

演算法速查

迴歸：Linear、Random Forest、Gradient Boosting ｜ 分類：Logistic、SVM、KNN ｜ 聚類：K-means、DBSCAN、Hierarchical

深度學習與生成模型

CNN 影像、LSTM 時序、Transformer NLP、PPO 強化學習；GAN 有模式崩潰風險、VAE 潛在空間平滑、Diffusion 品質最高

科目一 · 第五章 AI 技術應用與系統部署 ｜ 06 ｜ 模擬資料

選模型先看輸出是什麼。迴歸預測連續值，例如銷售額、房價，常用線性迴歸、決策樹、隨機森林、梯度提升；分類輸出離散標籤，例如垃圾郵件、疾病診斷，常用邏輯迴歸、SVM、KNN；聚類是非監督式，沒有標注也能自動分群，例如顧客分群，常用 K-means、DBSCAN、階層式。深度學習裡 CNN 做影像、LSTM 處理時序、Transformer 是 NLP 主流、PPO 用在強化學習；生成模型中 GAN 有模式崩潰風險、VAE 潛在空間平滑、Diffusion 品質最高。

5.2 系統集成 ｜ 資料管線與企業系統

模型要接進日常系統，才產生價值

資料管線

擷取 → 轉換 → 清理 → 入庫，確保資料持續流入

企業系統

ERP、CRM、POS、MES 接軌模型輸出

API 封裝

RESTful API、gRPC、Webhooks 提供推論服務

科目一 · 第五章 AI 技術應用與系統部署 ｜ 07

系統集成先建資料管線：擷取、轉換、清理、入庫，確保資料持續流進模型。模型以 RESTful API、gRPC 或 Webhooks 封裝成推論服務，再把輸出接回企業系統，例如 ERP 企業資源規劃、CRM 客戶關係管理、POS 銷售點系統、MES 製造執行系統，模型才真正進入日常營運。

5.2 系統集成 ｜ API 與 API Gateway

所有請求先過閘道：驗證、限流、路由

RESTful API

HTTP 動詞 GET／POST／PUT／DELETE＋URL 資源路徑，回傳 JSON

API Gateway

統一處理路由、身份驗證（OAuth2／JWT）、流量控管（Rate Limiting）

科目一 · 第五章 AI 技術應用與系統部署 ｜ 08 ｜ 示意流量

模型通常以 RESTful API 對外服務：用 GET、POST 等 HTTP 動詞加上 URL 資源路徑，回傳 JSON。前面再放一層 API Gateway 統一處理三件事：先用 OAuth2 或 JWT 驗證身份，再做流量控管，最後路由到對應服務。示意動畫中限流設定每秒五次，同一秒來了八個請求，前五個放行，其餘被擋下，回傳 429 太多請求。

5.2 系統集成 ｜ MLOps CI/CD

資料或程式一變，自動重訓、自動把關

CI 持續整合

程式碼或資料變動 → 自動觸發訓練＋測試

CD 持續部署

通過效能閾值後自動部署到生產環境

科目一 · 第五章 AI 技術應用與系統部署 ｜ 09 ｜ 示意準確率與閾值

MLOps 把 DevOps 延伸到機器學習。CI 持續整合：程式碼或資料一變動，就自動觸發訓練和測試；CD 持續部署：模型通過效能閾值才自動部署到生產環境。示意三次觸發，閾值設零點八九，第二次準確率零點九一才上線，第一次和第三次沒過，保留舊版。常用工具：MLflow 追蹤實驗參數與模型版本，DVC 管理訓練資料集版本，Prometheus 加 Grafana 做監控儀表板。

5.2 系統集成 ｜ Docker 與 Kubernetes

容器保證環境一致，編排負責自動擴縮

Docker

把程式與依賴封裝成容器映像 → 跨平台環境一致

Kubernetes

管理大量容器：部署、擴縮、負載平衡、故障恢復

微服務

拆成獨立小服務，各自部署擴展，透過 API 溝通

科目一 · 第五章 AI 技術應用與系統部署 ｜ 10 ｜ 示意流量；Pod 數 = ⌈流量 ÷ (容量 × 70%)⌉

Docker 把程式和它依賴的環境封裝成容器映像，在開發機、測試機、雲端跑起來都一樣，解決「在我電腦上可以跑」的問題。Kubernetes 管理大量容器的部署、擴縮、負載平衡和故障恢復。左圖示意一天的流量，水平自動擴縮依照每秒請求數除以每個 Pod 的容量乘以目標使用率七成，算出需要的 Pod 數：高峰時自動加到八個，離峰縮回最少兩個。微服務架構把系統拆成獨立的小服務，各自部署擴展，透過 API 溝通。

5.2 系統集成 ｜ 藍綠部署 vs 金絲雀部署

一次切換 vs 逐步放量

科目一 · 第五章 AI 技術應用與系統部署 ｜ 11 ｜ 示意流量比例

兩種發布策略。藍綠部署維護兩套相同的生產環境，藍色是現行版本，綠色是新版；新版先在綠環境部署測試，再一次把全部流量切過去，有問題可以秒切回藍色，零停機、可立即回滾，代價是要維護兩套環境。金絲雀部署先讓一小部分使用者，例如百分之五，用新版，指標正常再逐步放大到二十五、五十、一百，降低新版出問題的影響範圍。

5.2 系統集成 ｜ 監控與成效追蹤

三層 KPI，一層都不能漏

偵測漂移

Model Drift：預測分佈偏移
Data Drift：輸入統計特性改變

觸發再訓練

設效能下降閾值（如準確率降 5%）→ 啟動 Retraining Pipeline

A/B 測試

新舊模型隨機分流，比較業務指標的統計顯著性

科目一 · 第五章 AI 技術應用與系統部署 ｜ 12 ｜ 示意延遲資料

上線後要追蹤三層 KPI：系統層看延遲和吞吐量，應用層看準確率和 F1，業務層看 ROI 和轉換率。左下示意監控 P95 延遲，SLA 設一百二十毫秒，曲線一超過就發出告警。也要偵測模型漂移和資料漂移，並設定效能下降閾值，例如準確率下降百分之五，就自動啟動再訓練流程。要比較新舊模型，則用 A/B 測試隨機分流，看業務指標的差異是否達統計顯著。

部署模式 ｜ 公有雲、私有雲、邊緣、混合

依延遲、隱私、成本選擇落腳處

公有雲

按量付費、全球節點；挑戰：合規、供應商鎖定

私有雲

資料不外流；政府、金融、醫療；成本高

邊緣運算

本地推論、低延遲、省頻寬；資源有限、更新複雜

混合部署

兼顧算力與延遲；要設計資料同步，整合難度高

科目一 · 第五章 AI 技術應用與系統部署 ｜ 13 ｜ 圓點為相對程度示意

四種部署模式。公有雲如 AWS、Azure、GCP，彈性擴充、按量付費、全球節點，挑戰是資料隱私合規和供應商鎖定。私有雲如 OpenStack、VMware，資料不外流、安全合規性高，適合政府、金融、醫療，但成本高。邊緣運算在 IoT、手機、車載裝置本地推論，延遲低、保護隱私、省頻寬，但資源有限、更新複雜。混合部署是雲端訓練加邊緣推論，兼顧算力與延遲，但要設計資料同步與一致性，整合難度高。

03　邏輯迴歸

Logistic Regression

用於二元或多元分類的監督式學習模型，透過 Sigmoid 函數將線性組合輸出轉換為 [0,1] 機率值。適用於特徵與類別之間具線性可分性的場景。

📍 情境｜信用評分（高/低風險）、疾病診斷、客戶流失二元分類。

⭐ 考題｜「迴歸」名稱誤導，實為分類模型；多元分類用 Softmax 延伸（Multinomial LR）。

04　支持向量機

Support Vector Machine（SVM）

尋找使不同類別資料點之間間隔（Margin）最大化的超平面分類器。透過核函數（Kernel Trick）可處理非線性分類問題，適合高維資料。

📍 情境｜文本分類、圖像分類、生物資訊學（基因組資料分析）。

⭐ 考題｜SVM 對高維稀疏資料表現良好；大型資料集訓練慢；支持向量（Support Vectors）是最靠近決策邊界的樣本點。

隨機森林 ・ 梯度提升

05　隨機森林

Random Forest

集成多棵決策樹的 Bagging（自助聚合）方法，每棵樹用隨機子樣本與隨機子特徵訓練，最終以投票（分類）或平均（迴歸）整合預測，有效降低過擬合。

📍 情境｜信用風險、醫療診斷、股市預測、特徵重要性評估。

⭐ 考題｜Random Forest 提供 Feature Importance 分數，可用於特徵選擇；抗噪聲與過擬合能力強。

06　梯度提升

Gradient Boosting

集成學習方法，透過序列地訓練多棵弱分類器（通常是決策樹），每棵新樹修正前一棵樹的殘差（Residual），逐步提升模型準確率。代表：XGBoost、LightGBM、CatBoost。

📍 情境｜結構化資料競賽冠軍解法、金融風控評分、點擊率預測。

⭐ 考題｜Gradient Boosting 序列訓練（不可並行）；Random Forest 可並行訓練。XGBoost 是 Gradient Boosting 的優化實作。

K 均值分群 ・ 基於密度的分群演算法

07　K 均值分群

K-means Clustering

將資料點分配到 K 個群集（Cluster）的非監督式學習演算法，透過最小化每個點到所屬群集中心點（Centroid）的距離，迭代更新群集劃分直到收斂。

📍 情境｜顧客市場分群、文件主題分類、圖像色彩量化、異常偵測前處理。

⭐ 考題｜K-means 需預先指定 K 值（用 Elbow Method 選擇）；對初始點敏感；不適合非球形群集。

08　基於密度的分群演算法

DBSCAN

Density-Based Spatial Clustering of Applications with Noise，基於密度的分群方法，能識別任意形狀的群集，並自動將低密度區域的離群點標記為「雜訊（Noise）」。

📍 情境｜地理資料分析、異常點偵測、任意形狀群集發現。

⭐ 考題｜DBSCAN 無需預設群集數（K-means 需要）；能自動處理異常點；對高維資料效果較差。

09　自動化機器學習

AutoML

自動執行機器學習流程（特徵工程、模型選擇、超參數調優）的技術與工具。代表平台：Google AutoML、H2O.ai、AutoKeras、TPOT。降低 AI 開發的技術門檻。

📍 情境｜非專業資料科學家快速建模、企業快速原型驗證、AutoML 輔助特徵創建。

⭐ 考題｜AutoML 優勢：加速流程、降低門檻、高模型效能；局限：黑盒缺乏可解釋性、計算資源消耗大。

10　獨熱編碼

One-hot Encoding

將類別型特徵（Categorical Feature）轉換為二進位向量的編碼方式。每個類別對應一個位置，該類別為 1、其餘為 0。適用於無序類別（如顏色、城市）。缺點：高基數類別導致維度爆炸（Curse of Dimensionality）。

📍 情境｜城市名稱、產品類別、用戶職業等無序類別特徵的前處理；搭配 Logistic Regression、SVM 等模型。

⭐ 考題｜One-hot vs Label Encoding：Label Encoding 適用有序類別（如評分1-5）；One-hot 適用無序類別（避免模型誤判數值大小的意義）；Target Encoding 用類別的目標均值替代，避免維度膨脹。

遺漏值填補 ・ 交叉驗證

11　遺漏值填補

Imputation

處理資料集中缺失值（Missing Values）的技術。常見方法：均值/中位數/眾數填補（適合 MCAR 隨機缺失）、前向/後向填補（適合時序資料）、線性插補、KNN 填補（依相似樣本填補）、MICE 多重插補（多次迭代建模）。

📍 情境｜感測器資料斷訊填補、用戶問卷部分填答處理、醫療記錄缺失欄位補全。

⭐ 考題｜填補策略選擇依缺失機制：MCAR（完全隨機缺失）用均值；MAR（隨機缺失）用模型預測；MNAR（非隨機缺失）需謹慎；刪除策略（listwise deletion）在資料量夠大且缺失比例低時可用。

12　交叉驗證

Cross-validation（CV）

將資料集切分為 k 份（k-fold），輪流以一份為驗證集、其餘訓練，最終平均 k 次結果作為模型效能估計。避免單次分割的隨機偏差，更可靠地評估模型泛化能力。常見：5-fold、10-fold、留一法（LOOCV）。

📍 情境｜模型選擇與超參數調優時的評估標準；資料量少時（如醫療小樣本）的穩健評估方案。

⭐ 考題｜Cross-validation 用於模型選擇，最終以全部訓練資料重新訓練；避免 Data Leakage（資料洩漏）：前處理（標準化、填補）應在每折訓練集內計算，不能在整體資料上先做。

高維降維視覺化 ・ 資料增強

13　高維降維視覺化

t-SNE / UMAP

t-SNE（t-distributed Stochastic Neighbor Embedding）與 UMAP（Uniform Manifold Approximation and Projection）是非線性降維技術，將高維資料投影至 2D/3D 空間以視覺化聚類結構。t-SNE 保留局部結構；UMAP 速度更快且保留全局結構。

📍 情境｜深度學習特徵向量視覺化、顧客分群結果呈現、生物資訊（單細胞 RNA 分析）。

⭐ 考題｜t-SNE/UMAP 僅用於視覺化，不適合作為後續建模的特徵（因非線性轉換無法反向映射）；PCA 適合保留最大變異方向的線性降維，可用於後續建模；考試三者對比必記。

14　資料增強

Data Augmentation

透過對現有訓練資料進行變換（翻轉、旋轉、裁剪、亮度調整、加噪聲等）人工擴增資料集規模，減少過擬合、提升模型泛化能力。NLP 場景包括同義詞替換、回譯（Back-translation）。

📍 情境｜醫療影像分類（資料量不足場景）、工業缺陷偵測、CV 模型訓練；NLP 中資料稀少的低資源語言任務。

⭐ 考題｜Data Augmentation 是解決資料不足問題的核心手段（另有 Transfer Learning、GAN 生成合成資料）；增強策略需保留語義（如語義分割任務中 mask 需同步轉換）；過度增強可能引入雜訊。

15　資料管線

Data Pipeline

RESTful API

基於 HTTP 協議的應用程式介面設計風格，使用標準動詞（GET/POST/PUT/DELETE）和 URL 資源路徑，讓 AI 模型推論結果能被前端應用或其他服務呼叫。

📍 情境｜AI 推論服務封裝（Flask/FastAPI）、模型 API 供前端/APP 呼叫。

⭐ 考題｜REST 適合一般請求；gRPC 適合高效能雙向通訊；Webhook 用於事件驅動的非同步通知。

容器化與容器編排 ・ 微服務架構

17　容器化與容器編排

Docker / Kubernetes

Docker 將應用程式與依賴環境封裝為容器映像，確保跨環境一致性。Kubernetes（K8s）管理大量容器的部署、擴縮、負載平衡與故障恢復，是雲端原生 AI 部署標準架構。

📍 情境｜AI 模型跨平台部署、微服務架構、高可用性推論服務。

18　微服務架構

Microservices Architecture

藍綠部署 ・ 金絲雀部署

21　藍綠部署

Blue-Green Deployment

維護兩個完全相同的生產環境（藍色：當前版本，綠色：新版本），部署時將流量切換至綠色環境，若發生問題可立即切回藍色，實現零停機更新與快速回滾。

📍 情境｜AI 模型重大版本更新、零停機服務切換、快速回滾保障。

⭐ 考題｜Blue-Green：瞬間切換全量流量（低風險）；Canary：逐步灰度發布，小比例驗證後再全量。

22　金絲雀部署

Canary Deployment

將新版本模型先部署至一小部分用戶（如 5% 流量），監控效能指標無異常後再逐步擴大比例，最終全量切換。降低新版本問題的影響範圍。

📍 情境｜AI 推薦系統更新、LLM 新版本灰度測試、A/B 測試整合。

⭐ 考題｜Canary 名稱源自「礦坑金絲雀」預警概念；與 A/B Test 相比，Canary 更注重風險控制而非統計比較。

邊緣運算 ・ 模型監控

23　邊緣運算

Edge Computing

在靠近資料產生端的裝置（IoT 感測器、手機、車載系統）上進行模型推論的運算模式，將計算從雲端中心移至邊緣，大幅降低延遲並保護資料隱私。

📍 情境｜工廠即時品質檢測、自動駕駛感知決策、智慧城市監控、行動裝置 AI。

⭐ 考題｜邊緣推論特點：低延遲（Latency）、低頻寬消耗、高隱私保護；挑戰：算力有限（需模型量化/剪枝）。

24　模型監控

Model Monitoring

部署後持續追蹤 AI 模型在生產環境中的效能表現，偵測 Model Drift（預測分佈偏移）、Data Drift（輸入統計特性改變）及效能指標異常，及時觸發再訓練。

📍 情境｜金融風控模型維護、推薦系統效能追蹤、醫療 AI 持續品質保障。

⭐ 考題｜監控三層：系統層（延遲/吞吐量）、模型層（準確率/F1）、業務層（ROI/轉換率）；常用工具：Prometheus + Grafana。

推論延遲 ・ 模型版本管理

25　推論延遲

Inference Latency

AI 模型從接收輸入到返回預測結果所需的時間，是衡量 AI 系統回應速度的核心指標。高延遲影響用戶體驗，邊緣運算和模型輕量化是降低延遲的主要手段。

📍 情境｜即時推薦系統 SLA 要求（<100ms）、自動駕駛感知決策、即時詐欺偵測。

⭐ 考題｜降低 Inference Latency 方法：模型量化（INT8）、知識蒸餾、邊緣部署、GPU加速、批次推論（Batching）。

Model Versioning

📍 情境｜模型迭代更新管理、A/B 測試版本比較、合規稽核要求。

⭐ 考題｜MLflow Model Registry 提供模型版本管理（Staging→Production→Archived 狀態機）；DVC 管理訓練資料版本。

API 閘道 ・ 資料漂移

27　API 閘道

API Gateway

位於客戶端與後端 AI 服務之間的中間層，統一處理 API 路由、身份驗證（OAuth2/JWT）、流量控制（Rate Limiting）、負載均衡與監控日誌。AWS API Gateway、Kong、Nginx 是常見實作。

📍 情境｜AI 推論服務的統一入口管理；多模型 A/B 路由；防止 API 被惡意超量請求（DDoS 防護）。

⭐ 考題｜API Gateway vs Load Balancer：Gateway 側重請求路由與安全控制；Load Balancer 側重流量分發；AI 系統整合中，API Gateway 是暴露 ML 模型推論端點（RESTful/gRPC）的標準架構。

28　資料漂移

Data Drift

模型部署後，生產環境輸入資料的統計分佈發生顯著偏移（與訓練資料分佈不一致），導致模型效能下降。分為協變數漂移（輸入特徵分佈改變）與概念漂移（輸入-輸出關係改變）。需持續監控並觸發再訓練。

📍 情境｜電商推薦系統因季節性消費習慣改變導致效果下滑；詐欺偵測模型因詐騙手法演進失效。

⭐ 考題｜Data Drift（輸入分佈改變）vs Model Drift（預測輸出分佈改變）vs Concept Drift（底層關係改變）三者區分是必考重點；偵測方法：KS 統計量、PSI（Population Stability Index）、特徵統計監控。

A/B 測試 ・ 特徵儲存庫

29　A/B 測試

A/B Testing

將用戶隨機分為對照組（A：現有模型）與實驗組（B：新模型），在真實流量下比較兩組的業務指標差異，以統計顯著性判斷新模型是否優於舊版本。是 AI 模型上線決策的黃金標準。

📍 情境｜推薦系統新演算法驗證、廣告投放模型優化、LLM 回答品質比較評估。

⭐ 考題｜A/B Test vs Canary Deployment：A/B 強調統計比較（找更好的模型）；Canary 強調風險控制（安全切換）；A/B 需要足夠樣本量（統計功效 80%+）才能獲得可靠結論。

30　特徵儲存庫

Feature Store

集中管理、存儲和提供 ML 特徵的平台，支援特徵定義、計算、離線訓練（批次）與線上推論（即時）的一致性存取，避免訓練-服務偏差（Training-Serving Skew）。代表工具：Feast、Tecton、Hopsworks。

📍 情境｜金融風控即時特徵計算、推薦系統用戶行為特徵復用、多個 ML 模型共享同一套特徵管線。

⭐ 考題｜Feature Store 解決的核心問題：Training-Serving Skew（訓練時特徵計算邏輯與線上推論不一致）；離線 Store 供批次訓練（如 Parquet/Hive）；線上 Store 供低延遲查詢（如 Redis）。
